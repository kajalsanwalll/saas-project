Video SaaS

A cloud-native video processing platform — upload, auto-compress, and manage videos. Image transformation tool for social media formats. Built production-ready with Clerk auth, PostgreSQL, Prisma, and Cloudinary.

Next.js 16 TypeScript Prisma ORM PostgreSQL Cloudinary Clerk Auth Solo project SaaS / Full-stack
01 — Overview

What does it do?

Video SaaS has two core features: a Video Upload & Compression pipeline where users upload MP4 files (≤70 MB), Cloudinary auto-compresses them server-side, and the compressed version is stored with metadata in PostgreSQL via Prisma. Users see only their own videos on the dashboard.

The second feature is a Social Media Image Creator — users upload an image and pick from preset formats (Instagram, Twitter, Facebook). Cloudinary's transformation API resizes and crops the image on-the-fly; the browser previews it and downloads the final PNG without any server round-trip for the transformation itself.

Auth is handled entirely by Clerk — no password storage, no session tables, no custom auth logic. The userId from Clerk's JWT is the foreign key that links videos to users in the database.

02 — Architecture

Tech stack breakdown

Frontend
Next.js 16 + React 19

App Router, client components. shadcn/ui + DaisyUI for components. next-themes for dark/light toggle.

API Layer
Next.js Route Handlers

Three endpoints: /api/image-upload, /api/video-upload, /api/videos. All run on Node.js runtime (explicit export const runtime = "nodejs").

Database
PostgreSQL + Prisma

Relational DB via Prisma ORM. PrismaPg adapter with a connection pool (pg.Pool). Video metadata stored with userId FK from Clerk.

Auth
Clerk

Managed auth — no custom JWT, no password hashing. auth() in server components, getAuth(req) in route handlers, useUser() on the client.

Media Pipeline
Cloudinary

Videos: server-side upload stream → auto quality + MP4 format. Images: CldImage with crop=fill, gravity=auto for smart AI-based cropping.

ORM / DB Client
Prisma 7 + pg adapter

Global singleton pattern prevents connection exhaustion in serverless. PrismaPg uses the native pg driver (better performance than default Prisma connector).

03 — Data Model

Prisma schema (Video model)

model Video {
  id String @id @default(cuid())
  title String
  description String?
  publicId String // Cloudinary public_id
  originalSize String // bytes, stored as string
  compressedSize String // from result.bytes
  duration Float // seconds from Cloudinary
  userId String // Clerk userId FK
  createdAt DateTime @default(now())
}

No User table — Clerk owns user identity. userId is a string (Clerk's user_XXXX format) stored directly. This means no JOIN needed to get user info alongside videos, but you can't enforce a DB-level FK constraint to a users table.

06 — Interview Questions

Questions you'll be asked

Click to expand. Covers system design, security, scalability, and trade-offs — real patterns from Google, Meta, Amazon, and Microsoft loops.

01 DesignWalk me through the system architecture end to end. ▶
model answer

The app is a Next.js 16 monorepo with two user-facing features: video upload/management and social image transformation. The frontend is React 19 with client components for interactivity. The backend is three Next.js Route Handlers acting as REST endpoints — no separate server.

Auth is delegated entirely to Clerk — the userId from Clerk's session is used as a foreign key in PostgreSQL to associate videos with users. Media storage and processing is delegated to Cloudinary — the server streams file bytes to Cloudinary's upload API and saves the returned publicId and metadata to the database via Prisma.

The key architectural decision is offloading expensive work (encoding, transcoding, image transformation) to managed services, keeping the Next.js layer thin and stateless.

02 SecurityThe video upload API uses getAuth(request) but the videos GET endpoint reads userId from query params. What's the security issue? ▶
model answer

This is a real IDOR vulnerability (Insecure Direct Object Reference). The /api/videos?userId=xyz endpoint takes userId from the URL query string — anyone can substitute any userId and see another user's videos.

The correct fix is to read userId from the server-side Clerk session, never from client-supplied input:

  • Add const { userId } = await auth() inside the GET handler
  • Remove the userId query param entirely
  • Query: prisma.video.findMany({ where: { userId } }) using the verified server-side userId

FAANG signal: Mentioning IDOR by name and explaining why client-supplied identity is always untrusted shows security maturity. This is exactly the kind of self-aware bug identification interviewers at Google and Meta value.

03 DatabaseWhy PostgreSQL over MongoDB here? How does Prisma help? ▶
model answer

Video metadata is highly structured and uniform — every record has the same fields: title, description, publicId, size, duration, userId. There's no variable schema benefit from a document database.

PostgreSQL gives me: strict column types (no accidental string where int expected), ordering guarantees, foreign key constraints, and powerful aggregation (e.g. total storage used per user with a single SUM(compressedSize)).

Prisma adds type safety at the query layer — the TypeScript types for the Video model are auto-generated from the schema, so any mismatch between query and model is a compile error, not a runtime bug. It also provides migration tooling (prisma migrate dev) which gives a version-controlled audit trail of schema changes.

The trade-off: Prisma adds a query translation layer which is ~5-10% slower than raw SQL. For this app that's irrelevant. At 100M+ rows I'd consider Drizzle or raw SQL for hot paths.

04 ScalabilityYou call prisma.$disconnect() in every route handler's finally block. Why is this a problem? ▶
model answer

This is a real performance bug in the current code. Calling $disconnect() on every request tears down the database connection pool, then the next request has to re-establish it — adding 50-200ms of connection overhead per request.

The global singleton pattern already in lib/prisma.ts is meant to reuse the same Prisma client across requests. Disconnecting in the handler defeats this entirely.

  • Fix: Remove all prisma.$disconnect() calls from route handlers
  • Only disconnect in scripts (seed files, migration runners) that exit after completion
  • In production on serverless (Vercel), the process may be frozen between requests — the connection stays warm without needing manual lifecycle management

At scale the real fix is PgBouncer (a connection pooler that sits between your app and Postgres). Serverless functions can create hundreds of concurrent DB connections — PgBouncer pools them to a manageable number (e.g. 20) at the database level. Supabase and Neon have this built-in.

05 PerformanceThe video upload buffers the entire file into memory before streaming to Cloudinary. What's the problem and how do you fix it? ▶
model answer

Current approach: const bytes = await file.arrayBuffer() → Buffer.from(bytes) → uploadStream.end(buffer). This loads the entire file into Node.js heap memory. For a 70 MB file, that's 70 MB of RAM held per concurrent upload.

At 100 concurrent uploads that's 7 GB of RAM pressure — serverless functions typically have 128-512 MB limits. This will OOM crash.

Better approaches:

  • Presigned upload URLs: Generate a Cloudinary signed upload URL server-side and send it to the browser. The browser uploads directly to Cloudinary — the API server is completely out of the upload path. Zero memory cost, lower latency.
  • Streaming pipe: If server-side upload is required, pipe the request body stream directly to Cloudinary's upload stream without buffering: request.body.pipe(uploadStream) — but Next.js route handlers don't expose a raw Node stream easily.
  • Background job: Accept the file, store it in S3 temporarily, and process via a queue (BullMQ + Redis). Return a job ID immediately; client polls for completion.
06 DesignHow does Clerk auth work under the hood? How does the server verify a user's identity? ▶
model answer

Clerk uses short-lived JWTs (session tokens) stored in an HTTP-only cookie. On every request, Clerk's middleware (configured in middleware.ts) intercepts the request, reads the cookie, and verifies the JWT signature against Clerk's public key (fetched from Clerk's JWKS endpoint).

In route handlers, auth() or getAuth(request) reads the already-verified session from the request context — it doesn't make a network call to Clerk on every request. The JWT verification is local (crypto operation), fast (~1ms).

  • Token refresh: Clerk rotates tokens automatically every 60 seconds. The client Clerk SDK handles silent refresh in the background.
  • Revocation: JWTs can't be revoked mid-lifetime. Clerk's short expiry (60s) limits the blast radius of a stolen token.
  • userId format: Clerk userIds are prefixed strings like user_2abc... — storing them as String in Prisma (not UUID) is intentional.
07 ScalabilityHow would you scale this to 1 million users uploading videos? ▶
model answer

Current bottlenecks at that scale and the solutions:

  • Upload throughput: Move to presigned Cloudinary URLs — browser uploads directly to CDN, removing Next.js from the critical path entirely. API only handles metadata writes.
  • Database connections: Add PgBouncer or use Neon/Supabase's built-in pooler. PostgreSQL max connections (~100) can't handle 1M users without pooling.
  • Video processing queue: Cloudinary handles compression, but at scale you'd want async processing with status polling. Use a job queue (BullMQ + Redis on Upstash) to decouple upload from processing.
  • Read scaling: The /api/videos endpoint hits DB on every page load. Add Redis caching per userId (TTL 30s) — most users don't upload every 30 seconds.
  • Storage costs: At 1M users × 70MB avg = 70TB. Cloudinary pricing becomes significant. At this scale you'd move originals to S3 Glacier and serve only compressed versions via Cloudinary's fetch URL.
08 PerformanceHow does the social image transformation actually work? Does the server do any work per transformation? ▶
model answer

No — after the initial upload, all transformations are pure CDN. This is one of the best-designed parts of the app.

When the user selects "Instagram Square (1:1)", CldImage constructs a Cloudinary URL with transformation parameters baked in: something like https://res.cloudinary.com/{cloud}/image/upload/c_fill,g_auto,ar_1:1,w_1080,h_1080/{publicId}. The browser fetches this URL directly from Cloudinary's CDN edge.

  • First request: Cloudinary's origin server applies the transformation (AI gravity detection, smart crop), renders the result, caches it at the edge.
  • Subsequent requests: Same URL hits CDN cache — zero compute. Sub-100ms global delivery.
  • Download: The browser fetches the transformed image URL, converts to a blob, and triggers a local download — no server involved.

This is a perfect example of push work to the edge. The API server processes one upload; all transformations are free CDN operations. This is the scalability pattern FAANG engineers use for media delivery.

09 SecurityWhat are the other security issues you'd fix before going to production? ▶
model answer
  • File type validation: The video upload only checks accept="video/*" on the client. Server-side, we read the raw bytes — an attacker can send any file. Fix: check the file's magic bytes (first 4 bytes) server-side, or use a library like file-type to validate MIME type before uploading to Cloudinary.
  • No file size check in API: The 70 MB limit is only enforced in the frontend UI. The route handler has no size check — a malicious client can POST a 2 GB file. Fix: add if (file.size > MAX_SIZE) return 413 at the start of the handler.
  • Cloudinary credentials in env: NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME is exposed to the browser (that's intentional for CldImage), but the API key and secret are server-only. This is correctly handled — worth verifying .env.local never commits to git.
  • Rate limiting: No limit on how many videos a user can upload. A malicious user could exhaust your Cloudinary storage quota. Fix: add per-user rate limiting (e.g. 10 uploads/hour) using Upstash Redis with a sliding window.
  • Error messages leak internals: details: err.message is returned in 500 responses. This can expose stack traces, file paths, or DB connection strings. Fix: log full error server-side, return generic message to client.
10 Trade-offsWhy use Clerk instead of building your own auth? What do you give up? ▶
model answer

What you gain: Zero auth code to write. MFA, social logins, device sessions, bot detection, and GDPR-compliant user data storage out of the box. Clerk's security team handles all auth vulnerabilities — no risk of implementing JWT rotation wrong, missing CSRF, or storing passwords with a weak hash.

What you give up:

  • Vendor lock-in: Your userId format (user_XXX) is Clerk-specific. Migrating to another auth provider requires updating every FK in your DB.
  • Cost at scale: Clerk's free tier is generous (10K MAU), but at 100K MAU pricing kicks in. At large scale, custom auth is cheaper.
  • No user table: User profile data (email, name, avatar) lives in Clerk, not your DB. Any feature needing user data requires a Clerk API call or webhook sync to your own DB.
  • Cold start latency: Clerk's middleware runs on every request to verify the session. This adds a small overhead on serverless cold starts.

The right answer for an interview: "For an MVP or small team, Clerk is the correct trade-off — security is hard and auth bugs are catastrophic. At scale with a dedicated auth team, custom is worth it."

11 DesignHow would you add a video processing status tracker? (User sees progress while Cloudinary encodes) ▶
model answer

Currently the upload is synchronous — the client waits until Cloudinary finishes encoding, which can take 30+ seconds for a large video. This is a bad UX and risks request timeouts.

The right pattern is async job processing:

  • Step 1: API receives upload, stores file in S3 (fast), creates a VideoJob record in DB with status PENDING, returns jobId immediately (200ms response)
  • Step 2: A background worker picks up the job from a queue (BullMQ + Redis), uploads to Cloudinary, waits for encoding
  • Step 3: Worker updates VideoJob.status = COMPLETE and creates the Video record
  • Client polling: Frontend polls /api/jobs/:id every 3 seconds, shows progress bar
  • Better UX: Replace polling with Server-Sent Events (EventSource) — server pushes status updates as the job progresses. No wasted poll requests.

This decouples upload latency from encoding latency and makes the system resilient — if encoding fails, the job can be retried without re-uploading the file.

12 DatabaseYou store sizes as strings (originalSize: String). Why is that a problem? ▶
model answer

Three concrete problems:

  • Sorting is lexicographic, not numeric: ORDER BY originalSize would sort "9000000" after "10000000" alphabetically — wrong order
  • Aggregation is broken: SUM(originalSize) returns null for a String column — you can't calculate "total storage used by this user" without casting
  • No range queries: You can't write WHERE originalSize > 50000000 efficiently on a string column — it does a string comparison, not numeric

Fix: Change schema to originalSize BigInt and compressedSize BigInt. Prisma represents BigInt as BigInt in TypeScript. The reason it was stored as String originally is that JavaScript's Number type loses precision for large integers (>2^53) — BigInt solves this correctly.

13 Trade-offsWhat would you change if starting this project from scratch? ▶
model answer
  • Fix IDOR immediately: The userId-from-query-param vulnerability is the most critical thing. I'd never ship this to production.
  • Presigned uploads from day one: Bypassing the server for file bytes is architecturally correct and doesn't add complexity — just different API design.
  • BigInt for sizes: A 5-minute schema change that prevents subtle bugs and broken analytics later.
  • Remove prisma.$disconnect() from handlers: Easy fix, meaningful performance improvement.
  • React Query / SWR instead of manual fetch: The home page video fetch is a manual useEffect + useState pattern. SWR handles caching, revalidation, and loading states with 10 lines instead of 30, and gives background refresh for free.
  • Environment validation: Use zod to validate process.env at startup. Right now the app will silently fail at runtime if CLOUDINARY_API_KEY is missing — a startup crash with a clear message is far better.
